# BuoyCalc Windows

Windows-приложение для инженерного расчёта буйковой постановки на C# и Avalonia.

## Версия приложения и хронология репозитория

Пользовательская версия приложения пока остаётся:

```text
v0.46.4
```

Это отображаемая версия приложения, а не номер текущего архитектурного состояния репозитория. Историю последующих изменений нужно определять по Issues, Pull Requests и контрольным документам, а не по строке версии.

## Текущая фаза

На 6 августа 2026 года проект находится в фазе архитектурной стабилизации и инженерной верификации.

Последняя контрольная точка перед обновлением этого README:

```text
PR #237 — Diagnostics: verify segment and line-element current-force consistency
```

Расчётная физика, solver и пользовательские сценарии не расширяются побочно. Сначала фиксируется граница или дефект, затем выполняется минимальный проверяемый PR.

## Главные архитектурные правила

1. Инженерная физика живёт только в расчётном ядре.
2. PDF, 2D и UI только отображают уже рассчитанные данные.
3. Solver и численные формулы нельзя менять как побочный эффект рефакторинга, отчёта или визуализации.
4. Выбранная форма, stores и read models должны иметь явные границы и проверяемых потребителей.
5. Последовательность постановки остаётся произвольной цепочкой элементов, а не фиксированными участками 1/2/3.
6. 3D не входит в текущий объём проекта.
7. Архитектурные изменения выполняются маленькими Issue и PR.
8. Merge разрешён только после зелёных обязательных проверок.

## Зафиксированные инженерные границы

В текущем `main` уже присутствуют, среди прочего:

- последовательная модель элементов постановки;
- расчётные сегменты линии с локальной скоростью течения, плотностью, площадью, коэффициентом сопротивления, силой и весом в воде;
- сохранение принадлежности сегментной силы конкретному участку линии без опоры на редактируемый заголовок;
- сохранение локального веса каждого сегмента во всех путях расчёта натяжений;
- выбранная X/Z-форма и отдельные read models для отображения;
- проверочная векторная ведомость требуемых реакций;
- автоматические диагностические проверки согласованности длины, веса и силы линии между строками элементов и расчётными сегментами;
- отдельное отображение горизонтального модуля скорости течения и информационного 3D-модуля в техническом отчёте.

## Обязательные проверки

Каждый PR должен пройти:

```text
.NET Build
Selected Shape Consumer Scan
Report Store Consumer Scan
```

Нельзя объединять PR при `failure` или `pending`.

## Порядок продолжения проекта

1. Проверить актуальное состояние `main` и открытых PR/Issues.
2. Зафиксировать один конкретный дефект, несогласованность или архитектурную границу в отдельном Issue.
3. Для изменения поведения сначала добавить контрольный документ.
4. Выполнить минимальный production-PR без сопутствующего расширения области работ.
5. Проверить diff и обязательные workflow.
6. Объединить PR только после зелёного CI.
7. Следующий шаг выбирать по новому аудиту, а не по устаревшему номеру версии из README.

## Не входит в текущий этап

- добавление 3D;
- изменение solver без отдельной инженерной постановки и контрольной отметки;
- изменение физических формул вместе с UI, PDF или отчётом;
- крупные архитектурные перестройки одним PR;
- восстановление старого сравнения форм ради визуального эффекта;
- использование Markdown-отчёта как источника инженерной физики.

## Основной источник

Основной книжный источник проекта:

```text
Г. О. Берто. Океанографические буи.
Перевод с английского H. O. Berteaux, Buoy Engineering.
Ленинград: Судостроение, 1979.
```

Источник используется для инженерного обоснования. Реализованные формулы и допущения должны оставаться явно отделены от слоя отображения.
