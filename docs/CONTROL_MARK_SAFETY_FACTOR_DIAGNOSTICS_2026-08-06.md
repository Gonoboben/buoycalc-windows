# Контрольная отметка: источник и диагностика коэффициента запаса

Дата: 2026-08-06  
Issue: #286  
Область: расчётный result boundary и инженерная диагностика

## 1. Причина контрольной отметки

Пользовательский коэффициент запаса `SafetyFactor` проходит через `MainWindowCalculationInputBuilder` и передаётся в `BuoyCalculator.Calculate(...)`.

Он участвует в расчёте допускаемой рабочей нагрузки:

```text
WLL = MBL / SafetyFactor, если SafetyFactor > 0
WLL = 0, если SafetyFactor <= 0 или MBL отсутствует
```

После расчёта исходный коэффициент сейчас не сохраняется в `CalculationResult`. Поэтому downstream-диагностика видит только производные `WorkingLoadKn` и `TensionReserve` и не может надёжно различить:

- допустимый положительный коэффициент;
- нулевой или отрицательный коэффициент, который обнулил WLL;
- отсутствие MBL слабого звена, которое также приводит к нулевой WLL.

Восстановление коэффициента как `MBL / WLL` недопустимо: при ошибочных и неполных данных деление либо невозможно, либо теряет исходную причину.

## 2. Выбранная архитектурная граница

Источником истины для диагностики становится рассчитанный read model:

```text
CalculationResult.SafetyFactor
```

Поле содержит точное конечное значение `safetyFactor`, использованное `BuoyCalculator.Calculate(...)`.

Это значение является provenance расчётного входа. Оно не создаётся в отчёте, PDF, 2D или UI и не восстанавливается из производных величин.

## 3. Последовательность production-изменений

### Шаг A — result boundary

Отдельный behavior-preserving PR:

1. добавить `SafetyFactor` в `CalculationResult`;
2. передать в него существующий аргумент `safetyFactor` при формировании результата;
3. не добавлять потребителей и не менять вывод в этом PR.

Допустимый production-файл:

```text
Models/EngineeringModels.cs
```

### Шаг B — инженерная диагностика

Отдельный diagnostic-only PR добавляет строку:

```text
Коэффициент запаса слабого звена
```

Источник:

```text
result.SafetyFactor
```

Отображение:

```text
SF=<значение>
```

Допуск:

```text
SF > 0; рекомендуемое SF >= 3
```

Статусы:

```text
ERROR   — значение неконечно или SF <= 0
WARNING — 0 < SF < 3
OK      — SF >= 3
```

Порог `3` соответствует ранее принятому правилу проекта: коэффициент ниже 3 требует предупреждения, а нулевое или отрицательное значение является ошибочным.

Допустимый production-файл:

```text
Services/EngineeringDiagnostics.cs
```

## 4. Семантика результата и отчёта

Добавление поля в `CalculationResult` само по себе не меняет:

- `WorkingLoadKn`;
- `TensionReserve`;
- `Verdict`;
- `MainRisk`;
- строки `Checks`;
- существующий пользовательский результат;
- существующий технический отчёт.

После диагностического PR значение появляется в техническом отчёте только через уже существующую таблицу инженерной диагностики.

Отдельную строку итогов отчёта, новую PDF-формулу или UI-индикатор в рамках Issue #286 не добавлять.

## 5. Сохранение поведения

Не изменять:

- разбор и finite-нормализацию пользовательского ввода;
- WLL-формулу;
- выбор слабого звена;
- расчёт натяжений и индивидуальных резервов;
- расчёт удержания якоря;
- `CalculationResult.Verdict` и `MainRisk`;
- сегментацию 0,20 м и решение без ограничения числа сегментов;
- профиль течения, плотность, drag и волну;
- solver, gate и selected shape;
- 2D и PDF-координаты;
- project JSON/DTO;
- XAML и команды;
- версию приложения;
- 3D-область.

## 6. Проверки перед merge

Каждый PR допускается к merge только после успешных:

- `.NET Build`;
- `Selected Shape Consumer Scan`;
- `Report Store Consumer Scan`.

## 7. Не входит в эту задачу

Issue #286 не определяет отраслевой нормативный коэффициент для конкретного материала, срока службы, динамического режима или класса ответственности.

Порог `SF >= 3` является текущей проектной диагностической политикой. Любая будущая зависимость коэффициента от типа линии, материала, циклической нагрузки или нормативного документа должна оформляться отдельным инженерным изменением с верификацией формул.
