# Контрольная отметка: шаг сегментации 0,20 м без ограничения числа сегментов

Дата: 2026-08-06
Issue: #268
Scope: documentation only

## Решение владельца проекта

Расчётная линия должна разбиваться с целевым шагом:

```text
0,20 м
```

Ограничение общего или локального числа сегментов не вводится.

Это решение заменяет действовавший целевой шаг `1,0 м` и отклоняет предложенный предварительный предел `20 000` сегментов.

## Точное расчётное правило

В `BuoyCalculator.BuildSegmentRows(...)` сохраняется существующий алгоритм, но меняется константа целевого шага:

```text
targetSegmentLengthM = 0.20
segmentCount = max(1, ceil(itemLength / targetSegmentLengthM))
segmentLength = itemLength / segmentCount
```

Для каждого положительного участка линии:

```text
- число сегментов определяется отдельно по длине этого участка;
- итоговая длина каждого сегмента не превышает 0,20 м, кроме обычных эффектов представления double;
- сумма длин сегментов участка сохраняет исходную длину участка;
- нумерация и порядок сегментов сохраняются;
- участки с нулевой или отрицательной длиной продолжают обрабатываться по существующим правилам.
```

## Ограничения числа сегментов не допускаются

В рамках Issue #268 запрещено добавлять:

```text
- максимум сегментов одного участка
- максимум общего числа сегментов
- максимум суммарной длины линии
- автоматическое увеличение шага
- адаптивное укрупнение сетки
- отказ расчёта по оценочному числу сегментов
- UI preflight, блокирующий расчёт по размеру задачи
```

Приложение должно пытаться выполнить расчёт с фиксированным шагом `0,20 м` при любом конечном положительном значении длины.

## Это изменение расчётного метода

Изменение не является behavior-preserving refactor.

По сравнению с шагом `1,0 м` число сегментов при обычной длине возрастает приблизительно в пять раз.

Из-за более частого пространственного дискретизирования могут измениться:

```text
- глубины середины сегментов
- интерполированные U, V, W
- интерполированная плотность воды
- распределённая сила течения линии
- вес отдельных сегментов
- накопленные компоненты натяжения
- shape-based силы и натяжения
- fallback X/Z форма
- форма с дискретными элементами
- промежуточные и итоговые значения iterative solver
- число строк технического отчёта
- численные значения диагностик
```

При этом физические формулы не меняются. Меняется только пространственное разрешение их применения вдоль линии.

## Разрешённое production-изменение

Production PR должен изменить только одну строку в `BuoyCalculator.BuildSegmentRows(...)`:

```csharp
const double targetSegmentLengthM = 1.0;
```

на:

```csharp
const double targetSegmentLengthM = 0.20;
```

Допускается эквивалентная запись `0.2` без изменения смысла.

## Инварианты

```text
- Math.Ceiling остаётся без изменения
- Math.Max(1, ...) остаётся без изменения
- segmentLength = itemLength / segmentCount остаётся без изменения
- порядок line items остаётся без изменения
- identity строк линии остаётся без изменения
- current-profile interpolation не меняется
- density fallback не меняется
- drag, weight, buoyancy, wave, tension, anchor и shape формулы не меняются
- критерии iterative solver не меняются
- gate, stores и selected-shape routing не меняются
- 2D и PDF остаются потребителями рассчитанных данных
- JSON/DTO, XAML, команды и версия приложения не меняются
- 3D не добавляется
```

## Примеры количества сегментов

```text
0,01 м  -> 1 сегмент
0,20 м  -> 1 сегмент
0,21 м  -> 2 сегмента
1,00 м  -> 5 сегментов
55,00 м -> 275 сегментов
380 м   -> 1 900 сегментов
418 м   -> 2 090 сегментов
```

Количество определяется отдельно для каждого участка линии, поэтому сумма `ceil` по участкам может отличаться от `ceil` суммарной длины.

## Принятый эксплуатационный риск

При отсутствии верхнего предела очень большие конечные длины могут привести к:

```text
- длительному синхронному расчёту на UI-потоке
- большому потреблению памяти
- созданию очень больших таблиц и read models
- зависанию или аварийному завершению процесса до формирования диагностики
```

Этот риск принят решением владельца проекта. В рамках Issue #268 его необходимо документировать, но нельзя скрытно снижать лимитом, адаптивным шагом или отказом расчёта.
